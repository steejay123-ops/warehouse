# اتصال جستجوها و فیلترهای تکمیلی به آدرس مرورگر (URL State Persistence - Phase 2)

این طرح جهت پاسخ به درخواست کاربر برای اتصال سایر فیلترها (به ویژه فیلدهای جستجو `searchQuery`) و تب‌های داخلی به URL ایجاد شده است. با اجرای این طرح، وضعیت جستجوی کاربر در صفحات مختلف با رفرش کردن صفحه از بین نخواهد رفت.

## تغییرات پیشنهادی

### ۱. کامپوننت Users (`users.ts`)
این صفحه دارای ۳ وضعیت نمایشی است که هنوز به URL متصل نیستند:
- متغیر `searchQuery` (فیلتر جستجوی متنی)
- متغیر `activeRoleTab` (تب‌های داخلی بخش نقش‌ها)
- متغیر `activePermTab` (تب‌های داخلی بخش مجوزها)
**اقدام:** خواندن این مقادیر از `route.queryParams` در `ngOnInit` و اعمال به‌روزرسانی URL با هر بار تغییر این مقادیر در رابط کاربری (با استفاده از رویداد `ngModelChange` یا متدهای موجود).

### ۲. کامپوننت Projects (`projects.ts`)
این صفحه دارای متغیر `searchQuery` برای جستجوی پروژه‌ها است.
**اقدام:** تزریق `ActivatedRoute` و `Router`، خواندن `?q=` در `ngOnInit` و به‌روزرسانی URL در تغییرات ورودی جستجو.

### ۳. کامپوننت Customs (`customs.ts`)
این صفحه دارای متغیر `searchQuery` برای جستجو در کارتابل مالی است.
**اقدام:** از آنجا که این صفحه کش می‌شود (`reuse: true`)، خواندن `?q=` در متد `syncTabFromUrl()` (که می‌توانیم نام آن را به `syncStateFromUrl()` تغییر دهیم) و به‌روزرسانی URL در متد `onSearch()`.

### ۴. کامپوننت Counter Dashboard (`counter-dashboard.ts`)
این صفحه دارای متغیر `searchQuery` است.
**اقدام:** مشابه Customs، متغیر `q=` را در رویداد `NavigationEnd` خوانده و هنگام اعمال سرچ URL را به‌روزرسانی می‌کنیم.

## نحوه پیاده‌سازی به‌روزرسانی URL برای `searchQuery`
از آنجا که رویداد جستجو معمولاً با هر بار تایپ کردن کاربر و یا زدن دکمه اینتر فایر می‌شود، برای جلوگیری از پر شدن بیش از حد History مرورگر، در `router.navigate` از گزینه `replaceUrl: true` (برای جستجوهای زنده متنی) استفاده خواهیم کرد.
